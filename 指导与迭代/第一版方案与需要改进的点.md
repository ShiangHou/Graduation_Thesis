# 长候选列表大语言模型重排序：第一版方案与需要改进的点

**整理日期：2026 年 10 月 13 日**

**状态：第一轮导师反馈归档，尚未确定第二版题目。**

**来源：**两份历史文档及本次用户转述的导师意见。历史方案、导师反馈和整理建议分别记录；建议不代表导师已认可，研究假设不代表实验结论。

## 一、第一版：此前准备研究什么

### 1. 题目及演变

| 材料 | 重排方向题目 | 定位 |
|---|---|---|
| [选题第一版，第三章](第一版原始材料/选题第一版.md) | 面向金融搜索的长列表大语言模型重排序与稳健性优化方法研究 | 最初六方向初筛中的方向二 |
| [深度筛选报告，第四章](第一版原始材料/毕业论文选题可行性深度筛选报告.md) | 面向长候选列表的上下文敏感重排序与预算自适应比较方法研究——以金融检索为验证场景 | 后续筛选中的方向 B |

这里的“长序列模型重排”，按原文具体指**较长候选列表上的大语言模型重排序**。候选数量多、输入 token 长以及输出排序序列长是不同因素，后续问题定义需要区分。

### 2. 业务来源与任务设定

历史材料描述：多来源检索或工具召回得到约 200 条候选，系统希望输出 Top20，并可能给出排序理由。原方案关注候选增加时的排序质量下降、输入顺序敏感、候选 ID 错漏及推理开销。

原定任务可概括为：输入查询及上游召回的候选集合，由重排模型选出并排列 Top-K，使结果相关、稳定且计算成本可接受。这些现象在历史材料中作为实习观察和研究动机提出，当前仓库没有可供本次核验的实验日志。

### 3. 原方案的问题与方法安排

最初方案并列提出了三项问题：

1. 为什么候选数量增长后排序质量下降，是上下文长度、比较困难、位置偏置还是生成式 ID 错误造成的？
2. 如何得到全局一致的 Top-K 顺序？
3. 如何减少生成开销并保留相关性解释能力？

用户在本次沟通中将此前的组织方式概括为“为什么出现这个现象、出现了什么现象、用什么方法解决”。两种表述共同暴露的问题是：研究对象、原因分析、优化目标和方法设计混在一起，难以识别唯一的中心问题。

初稿方法包括层次化排序、全局校准、位置一致性约束、短解码和独立理由生成。后续报告进一步提出两个候选模块：一是估计和校正批次上下文相关误差；二是依据不确定性和 Top20 稳定性自适应分配比较预算。以上均是待验证设计，并非已经完成的方法或确认的创新点。

### 4. 原有实验准备与边界

- 以 BEIR-FiQA 为主要金融检索评测场景，另选检索域验证泛化。
- 固定上游候选，比较不同候选规模和输入排列；使用传统初排、pointwise、setwise、listwise 及相关方法作对照。
- 同时关注相关性、排列稳定性、token 用量、时延和输出合法性。
- 历史报告已经写到“报告上游 Recall@100/200”“重排不能找回未召回文档”，但尚未充分说明：在什么查询与候选质量条件下，重排仍是值得单独研究的瓶颈。

历史报告还指出既有工作与位置校准、上下文比较和预算分配等思路重叠。此处仅保留这一历史判断，本次不作新的文献核验或创新性结论。

## 二、导师本轮反馈

以下为用户转述内容的整理，不作为导师逐字引文。

### 反馈一：只明确一个具体问题

此前以“为什么出现、出现什么现象、如何解决”组织出多个问题，范围过宽。应从第一性原理出发，明确一个具体、可界定的问题，不应以宽泛的方法描述代替问题定义，也不应同时承诺解决三个问题。

**需要修改的核心：**先写清楚究竟哪一种错误、在什么条件下发生，再决定原因分析和解决方法如何服务于这个问题。现象、原因和方法可以构成同一研究的论证过程，不需要分别包装成三个研究目标。

### 反馈二：先回答上游和查询条件，再论证重排的必要性

重排高度依赖上游候选。对于精确查询，候选中可能只有一个最相关结果，固定取 Top20 时，后续结果未必符合需求；对于模糊查询，候选之间的关系及相关性判断又更复杂。若上游数据或召回质量不好，从第一性原理出发，可能应先优化上游，因此当前“为什么要优先研究重排”的论证还不充分。

**需要修改的核心：**不能默认所有查询都适合固定 Top20，也不能将上游缺少相关候选造成的低质量归因于重排模型。需要明确研究适用的查询、候选条件，以及改善上游后仍然存在的重排问题。

本轮意见要求补足研究边界和必要性，不能直接解释为导师已经否定全部重排研究，也不能据此认定必须转向上游召回。

## 三、第一版需要改进的点

下表为根据反馈整理的修改事项，供下一轮讨论，不是已确定的第二版方案。

| 优先级 | 第一版不足 | 修改要求 | 下一版应给出的材料 |
|---|---|---|---|
| P0 | 多个现象和优化目标并列 | 选择一个具体中心问题，其余只作为分析、约束或后续工作 | 一句话问题定义及明确的研究边界 |
| P0 | 默认输入长列表、输出 Top20 | 说明候选池大小 N 与结果数量 K 的来源；区分评测截断与业务实际需要 | 任务输入输出定义，固定 K 的适用条件 |
| P0 | 精确查询与模糊查询混在一起 | 定义查询类型并检查真实样例；不预设“精确必然只有一个相关结果” | 查询分类标准与代表样例 |
| P0 | 未充分区分召回失败与排序失败 | 检查相关结果是否进入候选池、进入后是否被排低 | 召回覆盖和候选内排序错误的分开统计 |
| P0 | 研究重排的必要性不充分 | 检查上游改善后是否仍存在可重复、具有价值的重排错误 | 上游改善前后的诊断及重排增益对照 |
| P1 | 方法先于问题，模块较多 | 中心问题确认后再挑选方法；不预先承诺去偏、效率、解释同时创新 | 一个问题对应一条方法主线 |
| P1 | 同时更改候选数量容易混入其他因素 | 区分候选集合变化、输入位置变化、文本长度变化 | 能隔离所选问题的受控实验设计 |
| P1 | 指标较多但主次不清 | 主指标与所选问题一致，稳定性和成本等按需作为辅助指标或约束 | 主指标、基线及继续/停止依据 |

## 四、下一轮讨论时先厘清的逻辑

### 1. 把候选缺失和候选排序分开

可以先按下面三个情形检查现有业务样例：

| 情形 | 需要先查什么 | 对重排选题的意义 |
|---|---|---|
| 相关结果没有进入候选池 | 数据覆盖、查询理解、召回及过滤过程 | 单纯调整候选顺序不能补回缺失结果 |
| 相关结果已进入候选池，却排在靠后位置 | 候选内的相关性判断和排序错误 | 才可能构成独立重排问题的证据 |
| 相关结果已靠前，后面被补入不符合需求的结果 | 输出数量、结果筛选和展示策略 | 可能涉及截断或拒绝输出，不应直接等同于排序错误 |

“只有一个相关结果”和“只有一个结果被标注为相关”也需要区分。不能把未标注文档直接视为不相关，或用稀疏标注证明某类查询只需要一个结果。

### 2. 固定上游只是隔离实验变量，不能单独证明选题价值

在同一候选集合上比较重排方法，有助于识别候选内的排序差异；但仅说“本文不研究上游”，不能充分回应导师。还应检查改善上游后该问题是否仍然存在，以及重排带来的增益是否值得其计算成本。

若错误主要来自相关结果缺失，或简单上游改善已经消除主要问题，应重新评估当前选题。若候选池中已有可用结果而模型持续排错，才能继续论证所选重排问题的独立价值。两种情况目前都未通过实验确认。

### 3. 暂不将修改建议写成新题目

下一步先完成一页问题定义，再决定是否改题。可以使用以下框架：

> 在【明确查询类型】与【明确候选条件】下，现有重排方法出现【一种可重复的具体错误】，导致【可衡量的损失】；本研究仅针对这一问题设计方法，并在【固定评价条件】下验证。

这里的空白不能仅用“长序列效果不好”“提高稳健性”填充。需要先从现有样例或预实验中获得证据，也不在本轮直接把“上下文误差”指定为最终中心问题。
